# 企业 Python Web 服务 PR 代码评审规范（Server SPEC）

---

## 1. 范围

本规范适用于企业级 Python Web 服务（FastAPI / Flask / Django / gRPC 等）的 Pull Request 评审，仅聚焦 PR diff 范围内的以下维度，不涉及代码风格、格式、命名偏好（由 linter/formatter 覆盖）：

- 正确性（Correctness）
- 边界条件（Edge Cases）
- 金额与精度（Money & Precision）
- 异常处理（Exception Handling）
- 超时控制（Timeout）
- 并发安全（Concurrency）
- 测试（Testing）

---

## 2. 评审检查项

### 2.1 正确性（Correctness）

- [ ] **业务逻辑分支**：`if/elif/else`、`match/case` 分支覆盖所有业务状态机状态；无遗漏的 `else` 默认路径导致未定义行为。
- [ ] **布尔逻辑**：`and/or/not`、`any()/all()`、空值短路语义正确；`is None` 与 `== False` 不混淆。
- [ ] **数据类型契约**：函数返回类型与调用方期望一致；JSON 反序列化后字段类型（`int`/`str`/`float`）在使用前已校验。
- [ ] **HTTP 状态码**：成功/失败路径返回语义正确的 status code（4xx vs 5xx），禁止所有异常统一返回 200。
- [ ] **数据库写操作**：`INSERT/UPDATE/DELETE` 的 `WHERE` 条件正确；`UPDATE` 未省略 `WHERE`；软删除与硬删除逻辑无误。
- [ ] **幂等性**：POST/PUT/PATCH 重复请求不产生副作用；关键写操作使用幂等键或唯一约束保护。

### 2.2 边界条件（Edge Cases）

- [ ] **空值与零值**：`None`、`""`、`[]`、`{}`、`0`、`0.0` 不会触发异常或产生错误分支；分页 `page=0`、`page_size=0` 有防护。
- [ ] **集合大小**：空列表迭代安全；单元素列表正确处理；超大集合（百万级）不会 OOM；分页有上限（如 `page_size <= 100`）。
- [ ] **字符串边界**：空字符串、超长字符串、Unicode 多字节字符（emoji、中文）在切片、截断、存储时不报错或乱码。
- [ ] **日期与时间**：闰秒、跨时区、夏令时切换、`datetime.min`/`datetime.max` 比较不溢出；朴素 datetime 与 aware datetime 不混用。
- [ ] **数值范围**：负数、最大值（`sys.maxsize`）、最小值、浮点数精度损失（`0.1 + 0.2 != 0.3`）场景已处理。
- [ ] **IDOR/越权边界**：资源访问前校验租户/用户归属；列表接口仅返回当前用户有权访问的数据。

### 2.3 金额与精度（Money & Precision）

- [ ] **禁止 `float` 存储/计算金额**：所有金额字段必须使用 `Decimal`（Python）或整数最小货币单位（分/厘），禁止 `float` 参与加减乘除、比较、序列化。
- [ ] **精度保留**：乘除后显式 `quantize()` 指定舍入模式（`ROUND_HALF_UP`）；除法不截断到错误位数。
- [ ] **货币一致性**：不同币种不直接相加；多币种字段带 currency code；汇率转换有来源与时间戳。
- [ ] **数据库存储**：金额列使用 `Numeric(precision, scale)` 或整数类型；JSON 传输使用字符串或整数，禁止浮点。
- [ ] **溢出与负数**：金额计算结果不能为负（退款/扣减场景除外）；总和不能因溢出导致符号翻转。
- [ ] **序列化**：API 响应中金额以字符串或整数形式返回，前端展示层负责格式化；日志中金额不丢失精度。

### 2.4 异常处理（Exception Handling）

- [ ] **不裸 `except:`**：禁止无类型的 `except:` 或 `except Exception` 吞掉所有异常（如 `KeyboardInterrupt`、`SystemExit`）；必须指定具体异常类型。
- [ ] **不静默吞异常**：`except` 块中必须 `raise`、`log.exception()` 或显式返回错误响应；禁止 `pass` 或仅 `log.error()` 后继续执行无效状态。
- [ ] **重试幂等**：对外部调用（HTTP、RPC、DB）的重试仅用于幂等操作；非幂等操作（如扣款）禁止自动重试。
- [ ] **异常转换**：底层异常（DB driver、HTTP client）在边界层转换为业务异常或统一错误响应，不直接暴露给调用方。
- [ ] **事务回滚**：异常路径确保数据库事务回滚；上下文管理器（`with session.begin()`）正确使用。
- [ ] **资源清理**：文件句柄、网络连接、锁在异常路径确保释放；使用 `with` 语句或 `try/finally`。

### 2.5 超时控制（Timeout）

- [ ] **所有外部调用有超时**：HTTP 请求（`requests`/`httpx`/`aiohttp`）、数据库操作、RPC 调用、Redis/MQ 操作必须显式设置 `timeout` 参数；禁止无超时的阻塞调用。
- [ ] **超时值合理**：超时阈值基于 SLA 设定，默认值不过大（如 HTTP 不超过 30s，DB 查询不超过 5s，短查询更低）。
- [ ] **超时后行为明确**：超时异常被捕获后有降级、熔断或快速失败策略；不重试风暴；超时错误计入监控指标。
- [ ] **请求总超时**：网关/框架级配置请求总超时，防止单个慢请求耗尽 worker；异步任务有执行时间上限。
- [ ] **连接池超时**：连接池获取连接有超时（`pool_timeout`），避免队列无限排队。

### 2.6 并发安全（Concurrency）

- [ ] **共享可变状态**：全局变量、类变量、模块级可变对象（`dict`/`list`）在多线程/多协程场景有锁保护或改为不可变/线程本地存储。
- [ ] **数据库并发写**：竞态条件（如库存扣减、余额更新、唯一名额抢占）使用乐观锁（版本号/`UPDATE ... WHERE version = ?`）、悲观锁（`SELECT ... FOR UPDATE`）或原子 SQL。
- [ ] **非原子操作**："先查后写"（read-modify-write）模式在并发下安全；缓存击穿/穿透场景有 singleflight 或分布式锁。
- [ ] **异步安全**：`async` 函数中不调用同步阻塞 I/O（需 `run_in_executor`）；`asyncio.Lock`/`Semaphore` 正确使用（同一 event loop）。
- [ ] **线程/协程泄漏**：手动创建的线程/任务在请求结束或服务关闭时被 `join()`/`cancel()`；后台任务有生命周期管理。
- [ ] **锁的粒度与死锁**：锁的持有范围最小；多锁场景全局一致加锁顺序避免死锁；锁有超时（`acquire(timeout=...)`）。

### 2.7 测试要求（Testing）

- [ ] **新增/修改逻辑有单测**：每个新增函数/方法至少有正常路径 + 边界路径测试；修改逻辑需覆盖被改分支。
- [ ] **金额精度测试**：金额计算测试用例覆盖：零值、负数（如适用）、小数位舍入、最大金额、跨币种。
- [ ] **异常路径测试**：Mock 外部依赖超时/异常/错误状态码，验证降级、重试、回滚、错误响应行为。
- [ ] **并发测试**：对竞态敏感的逻辑（库存扣减、唯一约束）有并发测试（多线程/协程/进程）验证原子性。
- [ ] **测试确定性**：测试不依赖网络、真实时间、随机数、执行顺序；使用 `freezegun`/`unittest.mock`/`pytest-mock` 控制外部因素。
- [ ] **Mock 行为正确**：Mock 返回值/副作用覆盖异常和超时；不 Mock 被测函数自身；断言 Mock 被正确调用（参数、次数）。
- [ ] **回归测试**：Bug 修复必须附带能复现 bug 的测试用例，该测试在修复前 fail、修复后 pass。

## 3. 发现格式

评审中每条发现必须严格遵循以下 Markdown 模板输出，缺一不可：

```markdown
### [严重级别] 简短标题

- **文件**：`path/to/file.py`
- **行号**：`L42`（或范围 `L42-L48`）
- **风险**：描述在生产环境下可能导致的具体后果（数据错误、资金损失、服务不可用、安全漏洞等）。
- **最小修复建议**：给出最小改动的具体修复方案，可附代码片段。禁止大范围重构建议。
```

### 3.1 严重级别定义

| 级别 | 标签 | 含义 | 是否阻塞合并 |
|------|------|------|-------------|
| 致命 | `[CRITICAL]` | 资金损失、数据损坏、生产崩溃、安全漏洞 | **是** |
| 严重 | `[MAJOR]` | 业务逻辑错误、异常未处理导致 5xx、并发竞态、超时缺失 | **是** |
| 一般 | `[MINOR]` | 边界条件遗漏但影响有限、测试缺失、降级不完善 | 否（建议修复） |
| 提示 | `[NIT]` | 可提升健壮性的建议，不影响正确性 | 否 |

### 3.2 发现示例

```markdown
### [CRITICAL] 金额计算使用 float 类型

- **文件**：`app/services/payment.py`
- **行号**：`L87`
- **风险**：`total = price * quantity` 中 `price` 为 `float`，浮点精度误差可能导致分账/对账金额偏差（如 0.1+0.2≠0.3），生产环境可能引发资金差错。
- **最小修复建议**：将 `price` 字段改为 `Decimal`，计算后 `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`；数据库列同步改为 `Numeric(18,2)`。
```

```markdown
### [MAJOR] HTTP 调用未设置超时

- **文件**：`app/clients/user_service.py`
- **行号**：`L33`
- **风险**：`requests.get(url)` 无 timeout 参数，若用户服务无响应将阻塞 worker 线程直至 TCP 默认超时（可能数分钟），高并发下耗尽线程池导致级联故障。
- **最小修复建议**：添加 `timeout=(3, 10)`（连接超时 3s，读取超时 10s），并捕获 `requests.Timeout` 返回降级响应或记录指标。
```

## 4. 测试要求（合并前置条件）

- **覆盖率门槛**：PR diff 中新增/修改的业务代码行覆盖率 ≥ 80%；核心支付/订单/风控模块 ≥ 90%。
- **必跑测试**：
  - 单元测试：所有新增/修改模块的单测全部通过。
  - 金额相关：必须包含 `Decimal` 精度/舍入/负数/零值测试用例。
  - 异常相关：必须包含外部依赖超时、连接失败、5xx 响应的 Mock 测试。
  - 并发相关：对 read-modify-write 模式必须包含并发测试（≥ 10 并发线程/协程）。
- **禁止项**：
  - 禁止跳过（`@pytest.mark.skip`）无理由的测试。
  - 禁止使用 `sleep()` 等待异步结果，必须用事件/条件变量。
  - 禁止测试依赖真实外部服务（DB 可用 testcontainers 或本地 SQLite in-memory）。
- **CI 校验**：以上条件不满足则 CI 标红，PR 不可合并。

## 5. 限制与合并门禁

### 5.1 评审范围限制

- **仅评审 diff**：评审者仅对 PR 变更行负责，不要求审查 diff 外的历史代码。
- **不阻塞于风格**：命名、格式、import 排序、注释风格等由 automated tooling（`black`、`ruff`、`isort`、`mypy`）强制执行，评审人不在评论中讨论。
- **不扩大范围**：评审意见聚焦当前变更，不要求顺带重构无关模块（scope creep 违规）。
- **单次 PR 规模**：单 PR diff 不超过 400 行（不含测试/生成代码）；超过则要求拆分。

### 5.2 合并门禁（Merge Gate）

PR 合并必须同时满足以下全部条件：

| 门禁项 | 要求 |
|--------|------|
| 致命/严重发现 | 0 个 `[CRITICAL]` 或 `[MAJOR]` 未解决发现 |
| CI 测试 | 全量测试通过，覆盖率达标 |
| 金额逻辑 | 所有金额字段使用 `Decimal`/整数，有精度测试 |
| 超时配置 | 所有外部 I/O 调用均有显式超时 |
| 异常处理 | 无裸 `except`、无静默吞异常 |
| 并发安全 | 竞态写操作使用原子 SQL/锁，有并发测试 |
| Lint/Type Check | `ruff`/`mypy` 零错误 |
| 评审人数 | 至少 1 名同模块 Owner + 1 名跨模块评审人 Approve |

### 5.3 豁免流程

- 紧急 hotfix 可经技术负责人书面批准后临时豁免部分门禁，但必须在 24 小时内补齐测试和评审。
- 自动生成的代码（protobuf、OpenAPI client、migration）可豁免覆盖率和逐行评审，但金额/超时/异常相关的手写封装层不在豁免范围内。
